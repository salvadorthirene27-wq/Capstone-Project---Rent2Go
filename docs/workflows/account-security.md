# Account verification and recovery

Rent2Go keeps its existing managed Neon Auth identity service. A public user can create a renter account, sign in/out, restore a session, request email verification, and recover a forgotten password using a time-limited provider code. Agency membership/approval and Cosigner agreements remain separate business decisions. An email-verification badge confirms control of an address, not the authenticity of uploaded identity documents.

## Account identity and verification

The protected Account & security workspace and GET /api/account read the current authenticated identity with cookie-cache bypass. Stored application roles and suspension remain authoritative; a role supplied by the identity-provider user object cannot grant platform or agency access. The local actor mirror synchronizes only the trusted account email, preserving role and suspension. If an authenticated email changes, earlier email-update consent is not transferred to the new address: its effective preference becomes off and the user must explicitly save a new decision. Existing queued records still require matching actor/email/preference/source permission before dispatch.

POST /api/account accepts only SEND_VERIFICATION or VERIFY_EMAIL with a six-digit code. The email address is derived server-side from the exact current session. Client-supplied recipients and unknown fields are rejected. Origin, sign-in/current-actor state, strict payload and per-actor request limits protect the endpoint. Already verified accounts return their current status without requesting another email. A successful provider result must match the same account ID/address and contain emailVerified=true. Incorrect, missing, expired or unsuccessful codes never establish verification. Raw provider error details are not returned; codes and credentials are not logged or copied into application audit records.

Verification is requested explicitly from Account & security. There is no automatic verification mailing on sample sign-ins or registration. Existing unverified accounts can still sign in; email-update opt-in requires a verified current address. Verification uses Neon's existing shared code sender for the approved local-only installation. The application name is Rent2Go. Deployment still requires reviewing the provider's production email settings; the application Gmail outbox and managed Auth email configuration are separate.

## Registration and password recovery

Registration requests only name, email and password; no client role or agency permission is accepted. Password confirmation is required. The new-account form guides users to Account & security after sign-in. Existing sign-in supports password managers and pasted passwords, including existing provider-supported passwords. New/reset passwords use a12-to128-character form policy and confirmation; the managed service also enforces its configured password policy. OTP values accept paste and one-time-code autofill.

The public /login?mode=recover route requests a reset code. Feedback does not disclose whether a specific address has an account. Recovery has three separate screens: request a code, verify the reset code, then choose/confirm a new password. The password screen is shown only after the managed provider positively checks the code with type forget-password. The code remains only in component memory; it is not stored in browser storage, a URL or a hidden form field. The final password-reset endpoint independently revalidates and consumes the same code. A rejected/expired final reset returns to code entry and clears password fields. Resending or changing the email/code discards earlier verification. The requested email is pinned on both subsequent screens; using a different email explicitly returns to recovery. Duplicate submits and mode switches are blocked while requests are pending. Code resends have a client countdown plus provider rate limits. New password/code fields are cleared after success or a mode change; late responses after unmount do not update the removed interface.

The managed branch has revoke_sessions_on_password_reset=true. A completed reset revokes existing sessions; it does not change roles, agency approvals, source agreements, financial records or document verification. Successful reset returns to sign-in for the new password. Users enter their own new passwords and live codes during the walkthrough; no password, OTP table value or session token is read to bypass the workflow.

## Current-password rule

The user selected rejection of the current password, rather than historical password tracking. Rent2Go's auth proxy validates a bounded strict JSON reset request and trusted Origin, applies request budgets, and verifies possession of the exact reset code before any credential lookup. A narrow SECURITY DEFINER function with a fixed pg_catalog search path returns only the matching current credential digest to the server; it grants no direct managed-table, token, OTP or password-write access to the runtime role and no PUBLIC execution. The server compares the proposed password with the maintained Better Auth verifier. No plaintext password, digest or reset code is persisted in application logs, history, responses or application-managed browser storage.

A matching current password returns PASSWORD_REUSE without forwarding a reset or consuming the code. The interface keeps the confirmed-code step, clears both password fields and asks for a different password. A different password is forwarded to the existing managed reset, which independently validates/consumes its code and revokes sessions. Missing/unsupported credential state or an unavailable policy check fails closed. Other local password-mutation endpoints are blocked in favor of the supported code flow. This rule is enforced at Rent2Go's application auth proxy; independently administered Neon APIs/console policies remain controlled by the identity provider.

Migration033 adds the read-only policy function and its narrow runtime EXECUTE grant; managed Auth tables are not modified. Two isolated database cases verify function privileges and unchanged synthetic digests using minimal managed-schema-shaped fixtures. The actual application runtime also successfully compared an existing synthetic account's saved credential with its known sample password and a different candidate, without reading real-user passwords, writing credentials or sending mail.
